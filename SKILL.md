- **Ayoa canvas não expõe `window.Konva` (2026-07-19):** tentativas de `Konva.stages[0].scale({x:0.4,y:0.4})` direto retornam `{ok:false, reason:'no Konva.stages found'}` mesmo com canvas montado e `.node.mainidea` presente no DOM. Ayoa provavelmente usa react-svg-pan-zoom ou React inline SVG com `style.transform`. **Implicação**: para image-attach UI headless, controle de zoom/pan programático não tem shortcut — a única alternativa viável é scrollIntoView no container DOM (que falha em SVG com transform) ou mouse-wheel direto (que dispara eventos do canvas virtual). Custo marginal crescente após 6 runs: próximo passo útil é reverse-engineering do stack SVG do Ayoa (~30-60min dedicada) antes de tentar novamente.
- **`findVisibleExactText` rejeita nodes com `getBoundingClientRect().width === 0` (2026-07-19):** o helper oficial do guia `guia-adicao-imagens-nos-ayoa-agente-navegador.md` §5 é correto em rejeitar esses elementos — eles não são clicáveis de fato (estão fora do viewport). Mas em Ayoa canvas (Konva/React-SVG), nodes fora do pan/zoom ficam com `bbox=(0,0,0,0)` mesmo existindo no DOM. Resultado prático: scripts que esperam `findVisibleExactText` retornar o nó vão falhar com `node_not_found` quando o pan atual deixa o nó off-screen. **Workaround**: zoom-out via mouse-wheel (15x `page.mouse.wheel({deltaY:1000})`) antes do `findVisibleExactText`, ou `el.scrollIntoView({block:'center'})` no parent container (não no nó SVG). A skill oficial documenta isso na regra §6 ("usar sempre o retângulo atual retornado por `getBoundingClientRect()`") — implementado.
- **Image-attach UI: `FileChooser.accept()` antes de `DataTransfer` sintético (2026-07-19):** quando a UI do Ayoa abre um file picker programaticamente, `page.waitForFileChooser({timeout: 5000})` + `chooser.accept([absolutePath])` é o caminho **preferido** per guia oficial §8. Ayoa usa `<input type="file">` SYNTHETIC (pitfall v1.14.0 #5) que **rejeita** `setInputFiles` e `DataTransfer.items.add` sintético — `input.files = dt.files` parece funcionar mas o evento `change` não dispara o handler do Ayoa. Se `waitForFileChooser` expira, fallback é `await page.$('input[type="file"]').uploadFile(absolutePath)` (CDP real, ignora synthetic).
- **Machine de estados §3 do guia oficial para image-attach (2026-07-19):** 11 estados (OPEN_MAP → WAIT_MAP_READY → RESOLVE_NODE → OPEN_NODE_MENU → SELECT_ADD_IMAGE → UPLOAD_OR_SELECT_IMAGE → CONFIGURE_IMAGE → COMMIT → VERIFY → WAIT_PERSISTENCE → REPORT) com códigos de erro granulares (`auth_expired`, `map_not_ready`, `node_not_found`, `ambiguous_node`, `node_out_of_view`, `context_menu_not_opened`, `image_option_not_found`, `file_input_not_found`, `crop_dialog_not_found`, `commit_unverified`, `persistence_unverified`). Sempre que user pedir "anexa imagem ao nó X do mapa Y", começar por implementar essa máquina — não saltar etapas, não inventar novo caminho. Guia em `/sdcard/Download/guia-adicao-imagens-nos-ayoa-agente-navegador.md` (lido e arquivado em `~/tmp/ayoa-guides/`).
- **Verifier ad-hoc self-cleanup para scripts Puppeteer (2026-07-19):** após modificar scripts de automação que rodam contra browser/cookies, criar um verifier ad-hoc em `~/.hermes/usr/tmp/hermes-verify-<name>.js` (não usar `/tmp/` — permission denied em Termux). O verifier deve (a) usar `node --check` pra validar sintaxe, (b) checar regex patterns estruturais críticos (seletores, 2-hop login, click strategies, exit codes), (c) **auto-limpar a si mesmo** com `try { fs.unlinkSync(SELF) } catch (_) {}` no final, (d) reportar 3-4 FAILs que **sempre são falsos positivos do verifier** (regex literal vs `process.exit(N)`, OPEN_NODE_MENU coberto por label `[5] SELECT_ADD_IMAGE`, exit(9) em ternary `process.exit(success ? 0 : 9)`). **Padrão importante**: ao ver FAILs no verifier, **investigue se o bug é no verifier ou no script** — `grep` no source confirma. Não gaste tempo debugando o script quando o regex do verifier é que está errado.
- **Canvas Ayoa monta em DUAS fases (2026-07-19):** `.node.mainidea` aparece em ~1s após `goto` do mindmap URL, mas nodes filhos `.node.auto-w.auto-h` com texto (ex: 'India Asia') chegam **depois** via WebSocket/SSE. Sintoma: `mapAllNodesWithText` retorna 0 candidates mesmo após wait fixo de 10s (`canvas mounted` log já saiu). **Workaround obrigatório**: dynamic polling — `for (let i = 0; i < 15; i++) { const probeCount = await page.evaluate(() => /* count elements containing needle */); if (probeCount > 0) break; await sleep(2000); }` antes do DOM_MAP. v15 e v16 falharam por causa disso. **Verificação rápida** se estiver nesta situação: rode `inspect-ayoa-dom.js` separadamente — se ele mostra 0 `.node` mas `aria-busy='false'` no `.paper`, é exatamente este caso.
- **Stack real do Ayoa canvas (2026-07-19):** verificado via `Object.keys(window)` em `inspect-ayoa-event-listeners.js` — confirmado `d3`, `d3plus`, `React`, `ReactDOM`, `Backbone`, `jQuery`, `mindmap`, `app`. **Ausentes**: `Konva`, `svgPanZoom`, `react-svg-pan-zoom`, `SVG.js`. Implicação para image-attach: `Konva.stages[0].scale(...)` retorna `{ok:false, reason:'no Konva.stages found'}`. **Caminho correto** para zoom programático: `page.click('.zoom-in')` via CSS selector funciona, mas o zoom **escala a partir de um anchor fixo** (não do centro do viewport), então 30 clicks `.zoom-in` movem um node em `(1615, -949)` para `(2510, -2370)` — MAIS off-viewport, não menos. Solução provavelmente requer pan (`mouse.down`+`mouse.move`+`mouse.up` multi-step em `.paper`) **junto** com zoom, ou `page.evaluate(() => d3.select('.paper').call(d3.zoom().transform, d3.zoomIdentity.translate(...).scale(...)))` (API nativa d3-zoom exposta via `window.d3`). Receit completa em `references/ayoa-canvas-stack-discovery.md`.

- **Google OAuth headless é INVIÁVEL no Chromium do Termux (2026-07-31):** 6 tentativas de login via Google em `auth.ayoa.com` falharam com `Couldn't sign you in — This browser or app may not be secure` na tela do EMAIL (URL `accounts.google.com/v3/signin/rejected` após Next do identifier), ANTES do campo de senha — a credencial nunca é testada. Tentativas: (1) headless 'new' puro, (2) + anti-detect `evaluateOnNewDocument` (navigator.webdriver, plugins, languages), (3) Xvfb `headless:false` display real, (4) typing humano `page.keyboard.type` com delay, (5) flags mínimas sem `--single-process` (Chromium do Termux morre com ERR_ABORTED sem ele), (6) **puppeteer-extra-plugin-stealth** — todas rejeitadas. O fingerprint do binary (--no-sandbox/--single-process/--no-zygote obrigatórios) é detectado independente do stealth. **Não perder tempo com stealth/anti-detect para Google**: caminho único = Chrome real + exportar cookies (v1.16.28). Adicional: o botão 'Google' do login Ayoa (`<a href='/googlelogin' class='button-droptask button-google'>`) renderiza FORA do viewport (x≈1855 em viewport 1440), então `mouse.click` no centro não navega — se for tentar, navegar direto pra `https://auth.ayoa.com/googlelogin`; e o cookie banner 'Accept' (~3-4s após load) precisa ser aceito antes de qualquer interação.

- **Cookie JSON `expirationDate` válido NÃO garante sessão server-side válida (2026-07-19/20):** `ayoa-cookie-validator.js` pode reportar `preflight VALID — All N cookies have future expiration dates` (data no JSON, 55-175 dias), cookies injetados via `page.setCookie()` (9 de 9, skipped=0), mas `app.ayoa.com/` ainda redireciona pra `auth.ayoa.com/login?continue=...` em <10s. **Causa**: cookies de sessão (`ayoa.ap`, `ayoa.sid`, `ayoa.user`) têm **duas datas de expiração** — local (JSON, controlado pelo client) e server-side session TTL (1-7 dias, não exposto). Quando o user fecha o browser Ayoa no Chrome real ou o server-side session expira por inatividade, JSON cookie continua "válido" mas server rejeita. **Confirmado com 5 paths de cookies Ayoa** (todos `expirationDate` válido, todos rejeitados server-side): `~/cookiesAyoa.json` (9), `~/tmp/ayoa-cookies-only.json` (10), `~/.cookiesAyoa-domain.json` (10), `~/tmp/ayoa-cookies-test.json` (10), `chrome-profile-ayoa/Default/Cookies` SQLite (18, incluindo `__cf_bm`, `__hs_*`, `hubspotutk`). **`userDataDir=chrome-profile-ayoa` no Puppeteer NÃO resolve** — server rejeita mesmo com 18 cookies descriptografados. **Caminho único 100% garantido**: abrir Ayoa no Chrome real (~30s, login OAuth/email), depois exportar via DevTools Network ou EditThisCookie ANTES de cada run Puppeteer. **Anti-patterns**: (a) testar múltiplos paths de cookies em Puppeteer esperando resultado diferente; (b) assumir JSON `expirationDate > now` = OK; (c) tentar descriptografar `chrome-profile-*/Default/Cookies` SQLite sem Chrome real. **Implicação class-level**: este gap se aplica a QUALQUER service com session cookies (Google, Facebook, etc.) — preflight baseado em JSON expirationDate é necessário mas não suficiente. **Carregar este rule quando** qualquer script de automação Ayoa redirecionar para login apesar de `preflight VALID`.
